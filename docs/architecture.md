# 架構與可靠性

> 本文件承接 `codex/compute-relay-demo` 分支的設計,改以 Django + Django REST Framework 實作。

瀏覽器以同源 API 存取 Django。資料庫保存帳號、批次、工作、節點、執行紀錄、成果與事件;
使用者上傳的檔案與成果存於 `DJANGO_DATA_DIR`,不經 `MEDIA_URL` 對外,一律由通過權限檢查的 view 提供。

## 派工與租約

Agent 主動連線,節點不需開放入站連接埠。每 5 秒回報一次心跳,派工時給 20 秒租約。
租約逾時、機主關閉分享或超出開放時段時,中央服務結束該次 attempt,工作重新排隊。

`Attempt` 有兩個條件式唯一索引:同一節點、同一工作各自只能有一個未結束的 attempt。
派工在交易內以 `select_for_update()` 鎖定節點後建立 attempt,因此兩台節點不會搶到同一件工作。

結果回報時再次確認 attempt 仍未結束且屬於該節點,逾時後才送達的舊結果一律拒絕
(`ATTEMPT_NOT_ACTIVE`),避免覆寫已重新派工的工作。

工作生命週期:排隊 → 準備 → 執行 → 完成。執行失敗、機主收回、租約逾時都會回到重新排隊,
含首次執行最多三次(`MAX_JOB_ATTEMPTS`)。使用者取消不自動重試,可手動重送。批次中每個檔案獨立計算。

`run_scheduler` 每秒掃描逾期租約與失聯節點;重啟後依資料庫現況接續,不會宣稱工作成功,也不清除紀錄。
Agent 端另有獨立 watchdog,以單調時鐘判斷續約失敗即停止自己的容器,避免持續佔用 GPU。

## 公平派工與額度

排隊中的工作依 `User.last_dispatch`、建立時間排序,一位使用者取得派工後排到最後,
因此多人同時送件時會輪流取得設備。每位使用者另有同時執行上限(預設 2)與每日檔案數上限。

## 本機停止

Agent 的 `enable` 在其工作目錄建立 `ENABLED` 檔案,`stop` 移除它;watchdog 每 0.25 秒檢查。
停止只對本 Agent 目前的容器名稱執行 `docker rm -f`,不執行 GPU reset,也不影響其他容器。
Docker 引擎本身故障時無法保證停止時間,須在實機驗收紀錄。

## 任務隔離

容器綁定指定 GPU、無網路、唯讀根檔案系統、移除 Linux capabilities、禁止提權、限制 CPU/RAM/PID,
且只掛載該工作的輸入、輸出與固定模型目錄。使用者不能指定命令、映像、模型或任意參數;
任務類型與模型版本固定於 `core/profiles.py` 的任務目錄,目前開放 `asr` 與 `upscale`,
其餘為 `planned`(已定義介面與成果檔名,容器尚未建置,送出時由後端擋下)。

模型於 `agent prepare` 階段由官方來源下載,Whisper 固定 Hugging Face revision。
模型 SHA-256、容器 image ID、GPU UUID、驅動版本與自我測試輸出寫入機台本機紀錄,
之後每次執行前比對;硬體或模型變動就要重新測試。只有通過自我測試的任務類型會登錄到平台
(`capabilities` 驗證失敗時配對與心跳都會被拒絕)。

## 用量取樣與彙整

儀表板的資料不另外輪詢機台,而是搭在既有心跳上:每次心跳依取樣間隔(預設 60 秒)最多寫入一筆
`UsageSample`,狀態由平台依 attempt 與租借紀錄判定,不採信機台自述。

取樣只保留兩週,長期統計改存 `NodeDailyUsage`。彙整由排程器每 5 分鐘重算當日一次
(`aggregate_usage` 可手動重跑),為冪等運算:重跑同一天的結果相同,不會重複累加。
`interval_seconds` 以 15 分鐘為上限,節點離線一段時間再回來時不會把整段空窗算進使用時數。

`busy_seconds` 是「設備處於有工作狀態的時間」,`gpu_seconds` 則取自 worker 回報的實測值,
兩者用途不同:前者反映設備被佔用多久,後者反映實際運算量。報告中不應互相取代。

## 互動式租借

租借與固定任務共用同一條 Agent 通道與同一批節點,差別在於平台不定義容器內要做什麼。
狀態機在 `core/rentals.py`:`queued → starting → active → ending → ended`,
另有 `expired`(時數到期)、`failed`(啟動失敗或設備失聯)與 `cancelled`。

一台節點同時只會有一件工作或一段租借:`claim_job` 與 `claim_rental` 互相檢查對方的進行中紀錄。
機主須另行開啟 `allow_rental`,租借才會派到該設備。時數自 Agent 回報可連線時起算,
不含容器啟動時間;啟動逾 180 秒未回報即退回佇列改派其他設備。

使用中的設備失聯時不重新排隊,而是標記 `failed`:容器內的狀態無法轉移到另一台機器,
重新啟動一個空容器對使用者沒有意義,應由使用者自行決定是否重新申請。

**待決定:對外連線通道。** 機台位於 NAT 後方,平台不會主動連入機台,連線必須由機台端建立。
候選方案與取捨:

| 方案 | 做法 | 取捨 |
|---|---|---|
| 由機台建立具名通道(如 Cloudflare Tunnel、ngrok) | Agent 啟動容器後開通道,把網址與權杖回報平台 | 設定簡單,但流量經第三方服務,須先取得校方同意 |
| 自架中繼伺服器 | 機台以 WebSocket 連到平台,平台代理使用者流量 | 資料不出校,但平台需負擔頻寬,且要自行處理連線管理 |
| 僅限校內網路直連 | 機台開放固定連接埠,只接受校內來源 | 最簡單,但需要機台開 inbound port,與 §2.3 的設計原則衝突 |

在方案確定前,平台端流程已可運作,申請會停留在排隊中。

## 權限

- 帳號由管理者以 `import_users` 批次建立,密碼隨機產生;登入以 Django session,每帳號每分鐘 10 次上限。
- 寫入類 API 需通過 CSRF 驗證;對外以 HTTPS 提供時 cookie 僅走 HTTPS。
- 節點使用 Bearer token,資料庫只存 SHA-256;配對碼一次性、10 分鐘有效;撤銷設備即令 token 失效。
- 一般使用者只能存取自己的工作輸入、成果與批次下載,以及自己設備的設定。
- 租借的連線位址與權杖只回傳給租借者本人,租借結束時從資料庫清除。
- 用量資料只記錄設備層級的狀態與使用率,不含使用者上傳的內容。
- 管理者透過 Django Admin 管理帳號、設備與工作,可撤銷設備、取消工作。

此版本以受管理且信任的校內設備為前提,未實作機密運算或可信硬體認證。
Agent 回報的 CUDA、模型與硬體佐證無法抵抗惡意機主偽造;機主也可能接觸自己設備處理的檔案。
網路與容器限制降低誤操作影響,不能取代校方設備管理與使用同意。

## 測試證據的範圍

`tests/` 使用暫存資料庫與模擬節點,可重現同時搶單、租約逾時、機主收回與重試上限。
這些結果只驗證協定,不能證明 CUDA、三台實機或效能提升。
實機產生的成果、NVML 數據、容器 image ID 與 `scripts/benchmark.py` 的 JSON 才是對應的實測紀錄,
狀態見 [驗收表](acceptance.csv) 與 [實測紀錄](verification.md)。
